## 1. Анализ производительности

### 1.1 Hot paths (часто выполняемые операции)

| Операция | Эндпоинт | Частота | Причина |
|----------|----------|---------|---------|
| Получение списка товаров | GET /api/products | Очень высокая | Пользователи часто просматривают каталог |
| Получение корзины | GET /api/cart | Высокая | При каждом заходе в корзину |
| Получение товара по ID | GET /api/products/{id} | Высокая | Просмотр карточки товара |

| Регистрация | POST /api/users/register | Низкая | Только новые пользователи |

### 1.2 Медленные операции

| Операция | Причина медленности | Потенциальная задержка |
|----------|---------------------|----------------------|

| GET /api/cart | Запрос к MongoDB, расчёт суммы | 5-20 мс |
| POST /api/cart/items | Запросы к products и users, обновление | 10-30 мс |
| POST /api/users/register | Хеширование пароля, запись в БД | 20-50 мс |

### 1.3 Требования к производительности

| Метрика | Целевое значение |
|---------|------------------|

## 2. Стратегия кеширования

### 2.1 Какие данные кешируем

| Данные | Причина кеширования | TTL |
|--------|---------------------|-----|
| Список товаров | Часто читается, редко меняется | 60 секунд |
| Товар по ID | Часто читается, редко меняется | 300 секунд |
| Корзина пользователя | Часто читается, меняется при добавлении товаров | 30 секунд |

### 2.2 Выбранная стратегия: Cache-Aside

Приложение сначала проверяет кеш, при промахе загружает данные из БД и сохраняет в кеш.

**Схема работы:**
1. GET /api/products → проверка Redis
2. Если данные в кеше → возврат (быстрый ответ)
3. Если данных нет → запрос в MongoDB
4. Сохранение результата в Redis с TTL
5. Возврат данных клиенту

### 2.3 Инвалидация кеша

| Событие | Действие |
|---------|----------|
| Создание/обновление/удаление товара | Очистка всех кешей products |
| Добавление/изменение товара в корзине | Очистка кеша cart для конкретного пользователя |

### 2.4 Требования к Redis

- Память: 256 MB
- Eviction policy: allkeys-lru

## 3. Стратегия rate limiting

### 3.1 Выбранный алгоритм: Token Bucket

**Почему Token Bucket:**
- Позволяет обрабатывать кратковременные всплески запросов
- Простая реализация
- Возможность задать разные лимиты

### 3.2 Лимиты для эндпоинтов

| Эндпоинт | Лимит | Причина |
|----------|-------|---------|
| GET /api/products | 100 запросов/мин | Каталог — основной источник нагрузки |
| GET /api/cart | 60 запросов/мин | Корзина запрашивается часто |
| POST /api/cart/items | 30 запросов/мин | Защита от накрутки корзины |
| POST /api/users/login | 10 запросов/мин | Защита от брутфорса |
| POST /api/users/register | 5 запросов/мин | Защита от спам-регистраций |

### 3.3 Заголовки ответа

| Заголовок | Описание |
|-----------|----------|
| X-RateLimit-Limit | Максимальное количество запросов в период |
| X-RateLimit-Remaining | Оставшееся количество запросов |
| X-RateLimit-Reset | Время сброса лимита (Unix timestamp) |
| Retry-After | Количество секунд до следующего запроса |

### 3.4 HTTP статус-коды

| Код | Значение |
|-----|----------|
| 200 | Успешный запрос |
| 429 | Too Many Requests — превышен лимит |

## 4. Реализация

### 4.1 Используемые технологии

- **Redis** — In-memory storage для кеширования
- **Token Bucket** — алгоритм rate limiting
- **Motor** — асинхронный драйвер MongoDB
- **FastAPI Depends** — внедрение зависимостей

### 4.2 Кешируемые эндпоинты

| Эндпоинт | TTL | Стратегия инвалидации |
|----------|-----|----------------------|
| GET /api/products | 60 с | При CREATE/UPDATE/DELETE товара |
| GET /api/products/{id} | 300 с | При UPDATE/DELETE товара |
| GET /api/cart | 30 с | При любом изменении корзины |

### 4.3 Rate limiting эндпоинты

| Эндпоинт | Лимит |
|----------|-------|
| GET /api/products | 100/мин |
| GET /api/cart | 60/мин |
| POST /api/cart/items | 30/мин |
| POST /api/users/login | 10/мин |
| POST /api/users/register | 5/мин |
