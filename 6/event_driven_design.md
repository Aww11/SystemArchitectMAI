## 1. Анализ событий в системе

### 1.1 Определение событий (Events)

Событие — это факт, который уже произошёл в системе. События неизменяемы и описывают, что случилось.

| Событие | Описание | Когда возникает |
|---------|----------|-----------------|
| UserRegistered | Пользователь зарегистрировался | После успешной регистрации |
| UserLoggedIn | Пользователь вошёл в систему | После успешного логина |
| ProductCreated | Создан новый товар | После добавления товара в каталог |
| ProductUpdated | Обновлён существующий товар | После изменения цены/описания/остатка |
| ProductDeleted | Удалён товар | После удаления товара из каталога |
| CartItemAdded | Товар добавлен в корзину | После добавления товара в корзину |
| CartItemRemoved | Товар удалён из корзины | После удаления товара из корзины |
| CartCleared | Корзина очищена | После оформления заказа или ручной очистки |

### 1.2 Определение команд (Commands)

Команда — это намерение что-то изменить в системе. Команда может быть отклонена.

| Команда | Описание | Производитель | Может быть отклонена |
|---------|----------|---------------|---------------------|
| RegisterUser | Зарегистрировать пользователя | API Users | Да (username/email уже есть) |
| LoginUser | Войти в систему | API Users | Да (неверный пароль) |
| CreateProduct | Создать товар | API Products | Да (недостаточно прав) |
| UpdateProduct | Обновить товар | API Products | Да (товар не найден) |
| DeleteProduct | Удалить товар | API Products | Да (товар не найден) |
| AddToCart | Добавить товар в корзину | API Cart | Да (нет на складе) |
| RemoveFromCart | Удалить из корзины | API Cart | Да (товара нет в корзине) |
| ClearCart | Очистить корзину | API Cart | Нет |

### 1.3 Потребители событий

| Событие | Потребители | Действие |
|---------|-------------|----------|
| UserRegistered | Analytics, Notification | Отправить приветственное письмо, записать в аналитику |
| UserLoggedIn | Analytics | Записать в аналитику (активность) |
| ProductCreated | Search, Analytics | Обновить поисковый индекс, записать в аналитику |
| ProductUpdated | Search, Cache, Analytics | Обновить индекс, инвалидировать кеш |
| ProductDeleted | Search, Cache, Analytics | Удалить из индекса, инвалидировать кеш |
| CartItemAdded | Analytics, Recommendations | Обновить аналитику, пересчитать рекомендации |
| CartItemRemoved | Analytics | Обновить аналитику (брошенная корзина) |
| CartCleared | Analytics, Orders | Зафиксировать конверсию, создать заказ |

## 2. Проектирование Event-Driven архитектуры

### 2.1 Компоненты системы

```
┌─────────────────────────────────────────────────────────────────────┐
│                          API Gateway                                │
└─────────────────────────────────────────────────────────────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
        ▼                           ▼                           ▼
┌───────────────┐          ┌───────────────┐          ┌───────────────┐
│  Users API    │          │ Products API  │          │   Cart API    │
│  (Producer)   │          │  (Producer)   │          │  (Producer)   │
└───────┬───────┘          └───────┬───────┘          └───────┬───────┘
        │                          │                          │
        └──────────────────────────┼──────────────────────────┘
                                   │
                                   ▼
                    ┌─────────────────────────────┐
                    │     RabbitMQ (Broker)        │
                    │         Exchange:            │
                    │       "store_events"         │
                    │           Topic              │
                    └─────────────────────────────┘
                                   │
                                   ▼
                    ┌─────────────────────────────┐
                    │      Queue: analytics_queue  │
                    │         Binding: #           │
                    └─────────────────────────────┘
                                   │
                                   ▼
                    ┌─────────────────────────────┐
                    │    Analytics Consumer        │
                    │    (Subscriber)              │
                    └─────────────────────────────┘
```

### 2.2 Производители событий (Event Producers)

| Компонент | Публикуемые события |
|-----------|---------------------|
| API Users | UserRegistered, UserLoggedIn |
| API Products | ProductCreated, ProductUpdated, ProductDeleted |
| API Cart | CartItemAdded, CartItemRemoved, CartCleared |

### 2.3 Потребители событий (Event Consumers)

| Компонент | Потребляемые события | Назначение |
|-----------|---------------------|------------|
| Analytics Consumer | Все события | Логирование, метрики, мониторинг |
| (будущий) Notification Service | UserRegistered | Отправка email |
| (будущий) Search Service | ProductCreated, ProductUpdated, ProductDeleted | Обновление поискового индекса |

## 3. Проектирование взаимодействия через брокер сообщений

### 3.1 Выбор брокера: RabbitMQ

**Причины выбора:**
- Простота настройки и использования
- Поддержка различных протоколов (AMQP 0-9-1)
- Хорошая интеграция с Python через aio-pika
- Встроенный management UI для мониторинга

### 3.2 Формат сообщений

```json
{
  "event_name": "user.registered",
  "payload": {
    "user_id": "12345",
    "username": "john_doe",
    "email": "john@example.com",
    "first_name": "John",
    "last_name": "Doe",
    "created_at": "2026-05-16T14:00:00Z"
  },
  "timestamp": "2026-05-16T14:00:00.123456Z"
}
```

### 3.3 Exchange и Routing

| Параметр | Значение |
|----------|----------|
| Exchange name | `store_events` |
| Exchange type | `topic` |
| Routing key | Имя события (например, `user.registered`) |
| Queue | `analytics_queue` |
| Binding | `#` (все события) |

### 3.4 Гарантии доставки

| Гарантия | Реализация |
|----------|------------|
| At-least-once | Persistent messages + consumer acknowledgements |
| Durable queues | Очередь переживает перезапуск RabbitMQ |
| Persistent messages | Сообщения сохраняются на диск |

**Почему не exactly-once:** Для аналитики допустимы дубликаты, at-least-once даёт достаточную надёжность.

## 4. Применение паттерна CQRS

### 4.1 Применимость CQRS

CQRS (Command Query Responsibility Segregation) разделяет операции на:
- **Commands** — изменяют состояние (write)
- **Queries** — читают состояние (read)

В интернет-магазине CQRS применим частично:

| Операция | Тип | Write Model | Read Model |
|----------|-----|-------------|------------|
| Регистрация | Command | MongoDB (users) | - |
| Создание товара | Command | MongoDB (products) | - |
| Добавление в корзину | Command | MongoDB (users.cart) | - |
| Получение списка товаров | Query | - | Кеш (Redis) |
| Получение корзины | Query | - | Кеш (Redis) |

### 4.2 Синхронизация read и write моделей через события

```
Write Model (MongoDB)          Event Bus (RabbitMQ)          Read Model (Redis/Cache)
        │                              │                              │
        │  Command: CreateProduct      │                              │
        ▼                              │                              │
   [Сохраняем в MongoDB]               │                              │
        │                              │                              │
        │  Event: ProductCreated       │                              │
        └─────────────────────────────►│                              │
                                       │  Event: ProductCreated       │
                                       └─────────────────────────────►│
                                                                      ▼
                                                               [Инвалидация кеша]
                                                                      │
                                                                      ▼
                                                          Следующий запрос
                                                          обновит кеш из БД
```

### 4.3 Преимущества для магазина

| Аспект | Без CQRS | С CQRS + событиями |
|--------|----------|-------------------|
| Чтение каталога | Прямой запрос в MongoDB | Кешированный ответ (Redis) |
| Обновление данных | Прямая запись в MongoDB | Запись + инвалидация кеша |
| Аналитика | Синхронно (медленно) | Асинхронно (не блокирует пользователя) |
| Масштабирование | Ограничено | Read и Write модели масштабируются отдельно |

## 5. Схема потока событий

### 5.1 Поток регистрации пользователя

```
1. Пользователь отправляет POST /api/users/register
2. API сохраняет пользователя в MongoDB
3. API публикует событие user.registered в RabbitMQ
4. Consumer получает событие и логирует
5. (В будущем) Notification Service отправляет email
```

### 5.2 Поток создания товара

```
1. Админ отправляет POST /api/products
2. API сохраняет товар в MongoDB
3. API инвалидирует кеш Redis
4. API публикует событие product.created в RabbitMQ
5. Consumer получает событие и логирует
6. (В будущем) Search Service обновляет поисковый индекс
```

### 5.3 Поток добавления товара в корзину

```
1. Пользователь отправляет POST /api/cart/items
2. API проверяет наличие товара
3. API обновляет корзину в MongoDB
4. API инвалидирует кеш корзины в Redis
5. API публикует событие cart.item_added в RabbitMQ
6. Consumer получает событие и логирует
7. (В будущем) Recommendations Service обновляет рекомендации
```

## 7. Заключение

Event-Driven архитектура позволяет:
- Асинхронно обрабатывать аналитику без блокировки пользователя
- Легко добавлять новых потребителей событий (уведомления, поиск, рекомендации)
- Масштабировать read и write модели независимо
- Повысить отказоустойчивость (очереди RabbitMQ буферизируют события)

В текущей реализации реализованы:
- Producer для всех основных операций
- Consumer для аналитики и логирования
- Интеграция с RabbitMQ через aio-pika
- Гарантия доставки at-least-once
